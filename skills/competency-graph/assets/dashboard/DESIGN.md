# Dashboard template: design

Read this before changing `index.html` itself: its layout, tabs, colours, keyboard and screen-reader behaviour, empty and error states, and narrow panes. It isn't needed to build, refresh or apply changes from the dashboard; `references/dashboard.md` covers those. When the page's behaviour changes, change this file and the page's Instructions tab with it. When what the skill is or does changes (a note type, a link, a counting step, a file, a store collection, a script, a ground rule), change the page's How this works tab with it.

## What the page shows

The page opens on a header with the title and, at the top right on the title's first line, the page's own version ("Version 1.0.0", small and muted; *Page versions* below), then a sentence on what the page is for (every competency's claimed and supported level, measured against the chosen frameworks and the owner's job specs, so each claim can be backed before it goes into a CV, an application or an interview), a sentence that says what the data says now (domains the evidence supports at L4 Expert, and how many competencies are rated above and below the evidence), and one short line with the date the graph was read, the units counted and a pointer to Instructions and to How this works (how to change a level is on the Instructions tab, not repeated here). Below it, a bar that stays in view holds the tabs (**Overview**, **Competency frameworks**, **Job specs**, **Rate personal competencies**, **Rating gaps**, **General definitions**, **Framework competency definitions**, **Configuration**, **Instructions**, **How this works**) the **Reload data** bar, which shows itself only while a data file has failed to load (below), and the save toolbar, which shows itself only while a change is unsaved or saved and waiting to be applied. A **Configuration** tab holds the assessors (below) and, for an owner with frameworks, lists every framework and pathway in the requirements file with a checkbox; the Pathway dropdowns on the Competency frameworks and Framework competency definitions tabs show only the selected ones, and share one choice: a pathway picked on one tab is the one shown on the other. One tab shows at a time; the open tab goes into the link a reader copies, and a link to a tab (or to any element inside one, e.g. `#domains`) opens it. The purpose sentence is body size in the text colour; the result sentence is the largest text after the title; the last line follows it in smaller, muted type. In a pane of 56rem or more the header is two columns under the title, on the split the Overview's two lower cards use (4 to 5): the purpose sentence on the left, and the result sentence with the last line (`p.sp-asof`) under it on the right, so the header is about half as tall on every tab and the result is on the first line under the title; narrower, the three stack in that order. The tabs sit edge to edge, each label 0.75rem from the next, so all ten fit a 1240px pane with none cut off.

Each card has one sentence under its heading saying how to read it. Everything longer (the level rules, units, years, anchors and deemed claims, fit and the markers, Evidence and Basis, group minimums, saving, staleness, sectors, what is left out) is on **General definitions**. A rule is explained once there, not again in a card.

**General definitions** is written to be read, not looked up: nothing on it is closed. The first card says what the tab is and lists its topics as buttons (`data-jump`), each of which scrolls to a topic's card and moves focus to its heading. Then one card a topic (`.sp-ref`): Competencies and levels; How the supported level is worked out; Comparing a claim with the evidence; Framework pathways (cut without frameworks); Job spec scores; What is counted and what is left out. Inside a card each term has its own `h3`, one or two short sentences, and a table (`table.sp-rt`) wherever values are listed side by side: the four levels, what each supported level needs, the kinds of evidence and of recognition, Fit, Evidence, Basis, the group flags, the points, the bands. A table states what a value means; a sentence after it gives the one thing readers get wrong (Short measures against the requirement, not against the claim). These tables are prose, so they are set at body size (the data tables are caption size), wrap, and keep to 56rem; a row's term is its row heading. In a pane under 40rem each row becomes a block, the term first and each further cell under it with its column's name before it (`data-l` on every cell of a table with more than two columns), so nothing scrolls sideways; the table, its rows and its cells carry their roles in the HTML (`role="table"`, `row`, `rowheader`, `cell`…), since a table laid out as blocks can lose them and the one-writer rule lets a script set no `role`. A new term goes in the card it belongs to, as a row of an existing table where it is one more value of the same kind.

- The toolbar: unsaved-change count, **Save changes**, **Discard**. With nothing unsaved it gives the last save's result, or else how many saved changes are waiting for Claude; a new change clears the last save's message, so the line never says "1 unsaved change. Saved 1 change." A saved change put back to the note's own level and saved again is withdrawn (its document is deleted), never kept as a change from a level to the same level.
- **Rate personal competencies**: every competency, rated or not, with or without shareable evidence, with a Search box (each word typed must start a word in the competency's name or path, domain included), Domain, Fit and Framework filters, and a Claimed dropdown on each row. The search, the filters and the sort go into the dashboard's params (`dash.setParams`; read back with `dash.params()` when the tab first draws), so a copied link keeps them as it keeps the open tab. Rows are grouped by what needs attention (rated above the evidence, not rated with evidence, rated with no shareable evidence, rated below, matches, not rated with no shareable evidence), each group in tree order with children indented 2ch per level (hover a name for its path; "(under X)" when the parent sits in another group). The Competency, Claimed, Supported and Units headings are sort buttons (`aria-sort` on the heading): the grouping stays first and the sort applies inside each group; the first press sorts names A to Z and levels and units highest first, the second reverses, the third goes back to tree order. Grouping and the Fit filter go by the level the Claimed dropdown shows (an unsaved or saved change, else the note's), so the list shrinks as claims are fixed. A changed row says "unsaved" or "saved" after its name (muted, like "(under X)"; its dropdown's outline is the mark) and keeps its place while the reader works: the list regroups on the next search (once typing pauses), filter or sort, or 1.5 s after a change once the mouse pointer has left the table (and, from the keyboard or a touch screen, once focus has left it). A redraw gives focus back to the same row's control and keeps the first row in view where it was. An unrated row with evidence has a "Use LX" button that stages the supported level, and its group heading stages all of them at once; staged changes still need Save changes. "Missing for the next level" is shortened ("+2 led units · +1.9 led years"); it is a button, and pressing it shows the full text in place (hover shows it too, but a finger has no hover). Above the table, the changes saved and waiting for Claude are listed with a Withdraw each; more than five close under their count ("65 saved changes waiting…"), so the list never pushes the table down the page. A count line, a live region, says how many rows are listed. Each "Use LX" button is named for its competency ("Use L2 for Leasing/letting") for screen readers.
- **Domains**: claimed against supported level, units, organisations, years of work, years led, recognition. A footnote says a unit counts once in each domain it evidences (so the Units column adds up to more than the units in the graph) and that Competencies and Rated count the domain itself; when a domain has units but none names an organisation, a second says why its Organisations cell says "None named" (Rating gaps does the same for a competency). How the years are measured is on General definitions. **Show unrated domains** / **Hide unrated domains** sits above the table and appears only while some domain is unrated (as the Claimed dropdown shows it); unrated domains are hidden by default. It applies to this table only.
- **The gap marker**: wherever Claimed and Supported sit side by side (Domains, the pathway table, Rate personal competencies, Rating gaps), the Supported cell carries "▲1" when the claim (as the Claimed dropdown shows it, unsaved changes included) is one level above the evidence, "▼2" when two below, and nothing when they match; its accessible name says it in words ("Claimed one level above the evidence"). The marker is the cell's one status signal: the Supported pill itself stays neutral.
- **Held against required**: wherever a level held is compared with a level required (the pathway table's Evidence, the scorecard's Result), the word follows a small circle drawn in CSS: full when the level is met, half when something is held below it, empty when nothing is. What is short or missing is the heavier text, since it is what the reader is looking for; Met stays quiet.
- **Colour**: each colour has one meaning. Kinds of evidence (the timeline) take the host's chart colours, skipping the ones most palettes make green, red or amber; credentials are dark diamonds. Fit takes the status colours, and only fit does: red for a claim above the evidence (▲), green where the evidence reaches the bar (a claim below it ▼, or Meets), amber for Short, grey for Matches. Each meaning has one mark: no evidence is an empty dashed outline, stale evidence is hatched. The roles are custom properties on `.sp` (`--sp-fit-over` and the rest), so every view uses the same ones. A changed claim is outlined in the text colour, solid while unsaved and dashed once saved. Muted text (card notes, footnotes, captions, the tabs not open) is `--sp-muted`, the host's muted colour pulled a quarter of the way to the text colour: the host's own is one mid grey in both themes, 3.6:1 on the light panel, and the stand-in tokens the tests use are darker, so only a render under the real stylesheet shows it. No rule uses `--color-fg-muted` itself.
- **Evidence over time**: one lane per domain, units as bars, credentials as diamonds, a labelled line at the stale cutoff; units that ended before it are hatched. The cutoff is measured back from the day the graph was read (`asOf`, which every timeline row carries), as the checker measures it, not from the latest piece of evidence. **Show: All years / Last N years** (N is the stale threshold) redraws the chart on an axis that starts at the cutoff, with one tick a year: a long career otherwise squeezes the recent work into a sliver. There, a unit that began earlier is drawn from the left edge, units that ended before the cutoff are left out, a domain with nothing recent keeps an empty lane, and the stale line and hatching leave the legend. A unit is drawn in every domain it evidences, often in several lanes, so each lane is that domain's whole record; the card's note says so. The legend lists only the kinds of evidence drawn. Two credentials close in time sit one above the other rather than overlapping. Hover, or tap on a touch screen, for a unit's details.
- **Domains across industries** (domain × top-level sector), each sector named with its code in the classification after it, "Information (51)" (the `code` of the sector's note, which each row of the sectors data file carries; the code never breaks at its hyphen, the column for units with no sector has none, and a file built before the field shows the name alone), as the card's note says in the classification's own name ("its NAICS Canada code", the `kg:sectors` value a second time); sector names level above their columns, wrapped, wherever every word of every name fits its column (no blank corner); in narrower columns they are angled, a long one on two lines (the full name on hover), which keeps the heading row short; in a pane too narrow for a column per sector, each domain lists its sectors with their counts instead. Shading is in five steps scaled on the real sectors only, and each count's text colour is picked from its cell; The column for units with no sector, headed "Own work & credentials" (the data files' "No sector"; `OFF_LABEL`), is outlined, unshaded and left out of the scale. And **rating fit** per domain: every competency under the domain, as Matches, Rated below (▼), Rated above (▲), Not rated, and No evidence (an empty dashed segment), so each bar's total is the domain's competency count less the domain itself. Each bar ends with its total and its ▲ and ▼ counts; with the legend, that is the direction said twice, so the segments carry no glyphs.
- **Competencies rated differently from the evidence**: in two groups with counts, as on Rate personal competencies (rated above the evidence, then rated below it), each by domain and name, with what is missing for the next level. Grouping here follows the data, not unsaved changes.
- **Framework requirements by pathway** (only with a requirements file, §5): for each pathway of a professional framework, every competency it requires, the level, the competency in the graph that maps to it (through `externalRef`), **Evidence** (Meets, Short or None: the supported level against the requirement) and **Basis** (Evidenced; Attested (deemed), the owner's attestation in the note's `deemed` field, never counted as evidence; Claimed only; or Below LX, when neither the claim nor the evidence reaches it; a chosen competency needs L2). The columns run as the scorecard's do: Evidence beside the name, since it is the answer and the column still in view in a narrow pane, then Required, the personal competency, Claimed, Supported, and Basis last, beside the two levels it is read from. **Show unrated competencies** / **Hide unrated competencies** sits beside the Pathway dropdown and appears only while some requirement of the chosen pathway is unrated (as the Claimed dropdown shows it; a requirement not in the graph counts as unrated); unrated requirements are hidden by default, with their own state, apart from the Domains pair. The group flags are judged on every requirement of the pathway, listed or not, and a group heading shows even when all its rows are hidden. Within a group the competencies are listed alphabetically, whatever the file's order (`spAlpha`); rows under one printed rule or condition stay together, the rules in file order, and are sorted within it. A group may list its competencies in sub-groups (the requirements file's `subgroup` column: the specialisations within the Optional lists of Chan AFSE, Chan AGEN and Chan CXMDS): each sub-group is headed once (`th.sp-subgroup`, a lighter heading than the group's), under the group's rule, the sub-groups in file order and alphabetical within; a row under one names its group and its sub-group among its `headers`; a sub-group heading shows only while one of its rows is listed. The rule and the group minimum cover the whole group, whatever the sub-groups. Each group's rule is printed once; a condition on some of its rows sits above the rows it names, in words that say what it counts toward ("At most one of these four counts toward the Optional choices: …"; where the guide requires one of them at a set level, "One of these two is needed for Core: …"). The requirements file writes it "Only one of: A, B.", from a guide's one entry joined by "or"; the page names the competencies from the rows that carry it, hidden or not, with semicolons where a name has a comma of its own. A row's own condition ("may be taken to L3") follows its name. Two competencies mapped to one framework competency get a row each; the group minimum counts only the better one. The group minimum applies the conditions a guide puts on some rows: where one of several is required at a set level ("A or B" in Core), one at that level is enough; of several choices under one condition, only the highest is counted; a choice with a set level ("must be taken to L3") counts only at that level and asks nothing below it; and the one of several that Core takes (the lowest that meets its level) is not counted again among another group's choices ("whichever is not selected as core"). A rule longer than its first sentence shows that sentence ("Plus, …" on its own line, as in the guide) with the rest, a footnote or the later sentences, under a closed **More on this rule**. For a pathway grouped as Mandatory, Core and Optional (RICS APC, Chan AFSE, Chan AGEN, Chan CXMDS) each group heading says "Group minimum:" after the group's name, inside the label that stays in view (so it wraps under the name in a narrow pane instead of sitting off to the right), and carries two flags, "As claimed: meets all / short" and "As evidenced: meets all / short": as claimed, judged on the levels the Claimed dropdowns show (an unsaved or saved change, else the note's level; deemed competencies included), and as evidenced, judged on the supported levels only (documented evidence). Each requires every fixed level met, and each selection rule ("N to Level X" or "N to LX", including "Plus … from the full list", met from the owner's other competencies mapped to the same framework) satisfiable, counting each framework competency once at its best level. A rule is read up to its footnote, which starts at an asterisk after a space (" *If …", " * Candidates …"); an asterisk straight after a level ("two to Level 2*") only points to the footnote and is dropped. `test_dashboard.py` runs `spGroupStatus` on each form.
- **Framework competency definitions by pathway** (only with a requirements file and its descriptions file, §5): the chosen pathway's requirements by group (Mandatory, Core, Optional for RICS APC), one row per framework competency, alphabetically within the group (within each sub-group where the group has them, each headed as on Competency frameworks), with Required, a general **Description**, and what **L1 Aware**, **L2 Practitioner**, **L3 Advanced** and **L4 Expert** mean for it. The cell of the level the pathway requires is tinted and labelled "Required" (both cells, "Required (L2 or L3)", for "L2 or L3"; none for a chosen competency, whose rule gives its level). Under each description, "Source:" says where the wording came from: the framework's own text, the owner's own adaptation of it (for RICS APC, Reggie Chan's North American wording from his RICS-APC-prep repository), or text drafted for the graph where the framework has none. Wording that lists items ("including: • a • b", or ": - a - b") is shown as a lead sentence and a list. A draft framework says so above the table, as on Competency frameworks. In a pane of 72rem or more the five text columns share the card (each at least 10.5rem), so L1 to L4 are read side by side with no sideways scroll; in a narrower one each keeps its 15rem and the table scrolls. The descriptions are reference text, not evidence: they never change a level.
- **Job specs** (always, since the library ships with the skill): roles the owner defines from framework competencies. A **Spec** dropdown (each spec's title, marked "(saved here)", "(deleted here)" or "(unsaved)" for a spec not yet in the job specs file) with **New**, **Duplicate**, **Edit** and **Delete** (Delete asks first, in place: "Delete this spec?" with **Delete it** and **Keep it**, since a spec saved only on the dashboard can't be brought back); under it a status line saying where the spec on screen comes from, with **Withdraw** or **Use the file's version** for a change saved here. The verdict is a two-row table, **As claimed** and **As supported**, always both: Band and Promotion ("Ready" / "Not yet: <next role>", or "No next role set") first, since they are the answer and the first columns are the ones in view in a narrow pane, then Mandatory gate, Breadth and Depth ("12 of 14 (85%)", percentages rounded down) and Above the requirement (depth points, "+3 optional" beside); under it, one sentence each saying what kind of gap it is (broad but shallow, deep but narrow, even, or meets) and the spec's note. Gate and band words take the evidence colours: green Met / Baseline / Exceeds role, amber the rest. The **Scorecard** groups the spec's competencies by section, each group heading carrying its counts and points after its name; each row shows the framework competency (its framework after it), the **Result** (Met, Above, Short, Not held, Held, after its circle) beside the name, Required, the graph competency mapped to it ("Not in the graph", or "+1 more" when several map), a Claimed dropdown (the same staging as everywhere; one for a framework competency not in the graph stages a new-competency request), Supported with its gap marker, and three points columns headed with the basis being scored (**Claimed breadth**, **Claimed depth**, **Claimed credit above**; Assessed or Supported in place of Claimed): breadth and depth credited of required, capped at the level required, and the depth points held above it as +N (Optional shows only its credit). All three wordings of each heading are in the HTML as `data-basisword` spans, and `spJSControls` sets `hidden` on two of them, so no script writes header text. **Shortfalls only**, a pressed button beside Score on, lists just the Mandatory and Core requirements held below their level or not held ("No shortfalls…" when there are none). **Score on** (Claimed levels / Supported levels, a pair of pressed buttons) switches the scorecard's level, dropdown and points; the verdict ignores it. **Edit the spec** shows only while a spec is being edited, and while it is, the Spec dropdown and the four buttons are disabled: Title, Note, Next role up, Probation floor and Exceeds role fields; Save spec and Discard with a status line counting the competencies per section (or saying what stops the save) and giving the verdict as the spec stands ("As claimed: Probation (breadth 78%, depth 70%). As supported: …"), since the verdict card is up the page while the picker is in use; and a picker of framework competencies (Search, Framework, Show: *In the spec* or *All framework competencies*), each row with a **Section** dropdown (Not in the spec, Mandatory, Core, Optional), a **Required** level dropdown (dimmed until the competency has a section) and what the competency covers, with the chosen level's wording under it. A change in the picker updates the verdict and the scorecard at once and leaves the picker as it is, so the row being worked on doesn't move. **Compare specs** lists the specs with checkboxes (by default the ladder through the spec on screen, followed by `next`, else the first six) and draws a table, a column per spec, of each competency's section letter and required level, marking with "=" a cell that matches the role just below it in the ladder, with breadth and depth targets at the foot. With fewer than two specs there is nothing to tick, and the card says so and points to **Duplicate**. **Specialisations:** a framework competency that its framework lists in a sub-group (the `subgroup` and `subgroup_order` columns `dashboard_build.py` adds to the descriptions data; `spSubs`) shows it in all three places. In the scorecard each section lists its other competencies first, then each specialisation under a sub-heading ("Chan CXMDS: Data operations and quality", with how many of its competencies in that section are met, counted whether or not Shortfalls only lists them), the frameworks in name order and a framework's specialisations in its own order, the spec's order kept within. In the editor the specialisation sits under the framework's name and Search matches its words. In Compare specs it follows the framework's name in the brackets.
- **General definitions**: described above; its last card says what is left out (confidential evidence) and that the figures are a snapshot.
- **Instructions**: how to use the page, written for whoever opens it, all of it in the HTML (no drawing made by a script). A card on what the page is for with the tabs at a glance (a two-column list, so it keeps to a prose table's 56rem, not a line's 64ch); **Read the marks**, a table of the marks with each one shown as the tables show it (▲1, ▼1, the up-down mark for assessors who differ, the full circle, the solid and dashed outline, Failed to load with what to press, the dash); **Record new work** (asking Claude to write up or update the record of a role, what a strong line holds, the work-machine prompt, how often); **Have assessors rate the competencies** (a chain of six steps, `ol.sp-flow` as on How this works, then *Keep the list of assessors*, *Give the ratings* and *Read the result*); **Change a claimed level** as numbered steps (find it, change the dropdown or press Use LX, Save changes, then ask Claude to *apply my dashboard changes*; Discard and Withdraw; saving needs contributor access); **Measure the graph against a framework** (Configuration, the pathway table and its flags, Framework competency definitions, giving a level to a requirement not in the graph); **Build a job spec and score against it** (New, Duplicate or Edit, the form, the picker, Save spec and applying it, Score on); **Ask Claude**, with the requests that change the graph; and **Sharing and what readers see** (confidential left out, data files readable in full by anyone who can open the page, copied links keep the tab and filters, the figures are a snapshot). Its words describe the page's behaviour, so a change to how saving, the framework tabs or sharing works changes them too.
- **How this works**, the last tab: what the page and the skill behind it are and do, where Instructions says only how to use the page. It is written for a reader who has never seen the skill (an owner, an assessor, someone deciding whether to use it), and all of it is in the HTML: no dataset, no script writes into it, and it names no owner, so it reads the same on every owner's dashboard. The first card says what the system is and lists its topics as buttons (`data-jump`, as on General definitions). Then a card a topic, each a `.sp-ref` card with the same headings, prose tables (`table.sp-rt`) and line length as General definitions: **The three parts** (the owner's files are the record, the skill is what Claude runs, the dashboard is a display; the loop between them); **The graph** (three kinds of note, the seven links, discipline and sector as two axes, each link stored once, taxonomy against ontology); **How records are stored** (a note is a markdown file with its fields at the top, with a competency note and an evidence note set out as samples; what is kept in which file; what is stored and what is worked out; how a note is changed); **Where the evidence comes from** (the six steps from the owner's records to checked notes; *The record behind a job*, the method of `references/recording-experience.md` as a chain of steps, with what each part of a HAM-Z line becomes in the graph; the rules that keep evidence honest; the three levels of disclosure); **From evidence to a supported level** (units, roll-up, the counts, the level rule); **Claimed, assessed and supported** (who sets each reading and where it is kept, the assessed level as the lowest of the assessors' ratings, who the assessors are, what a difference between them means); **Frameworks and job specs** (a personal competency names a framework competency; pathways and job specs ask for it); **How this page is built, where a change waits, and how it gets back** (what the build writes; the dashboard's own database, named as a database, with who writes each collection, `files` and `datasets` by Claude at each build and `claims`, `jobspecs` and `settings` by the page on a save; the six steps from a changed dropdown to the rebuilt page); **What the skill is made of** (its parts, and what it does not do). The reader's word for the store is **database** (the dashboard's database; a note is never said to be in one): the tab says the record needs no database and that the dashboard has one, because a reader who changes a level asks where it went. It explains mechanisms and leaves each rule's detail to General definitions, which it points to: a threshold is stated there once, and the one this tab quotes (five years led, in a caption) carries its `kg:` marker.
  - **Drawings** (`figure.sp-fig`): six, each an inline SVG with `role="img"`, an `aria-label` that says in words what the picture shows, and a `figcaption` giving its one claim. They are in the text colour only, since on this page a hue means fit or a kind of evidence: a box is a tint of the text colour, a dashed outline is something worked out or kept outside the graph (the supported level, a framework competency), a pale outline is a place (the owner's folder, claude.ai), and every arrow is labelled. Shapes and text take their look from the page's stylesheet by class (`n`, `q`, `z`, `e`, `h`, `k`, `m`, `b`); an SVG holds no `<style>`, no `<script>`, no `id` and no `url(#…)`, and each arrowhead is its own `<polygon>`, so nothing depends on a host keeping ids. All share a 720-unit-wide `viewBox` and are shown between 36rem and 45rem wide, so their text stays between about 9px and 13px; the host's font sets wider than the stand-in, so a label is given its room as measured under the real stylesheet (a box's text 10 units clear of its edge, an arrow's label 5 clear of the boxes it sits between), and a line too long for its box takes two; in a narrower pane the drawing scrolls sideways in a `.sp-scroll` wrapper, which gets the edge fade and a Tab stop from the scrolling script like any wide table.
  - **A marked line** (`p.sp-hamz`, here and on Instructions): one example bullet with its four HAM-Z parts underlined and lettered (`span[data-p]`; the letter is CSS content with empty alternative text, and the table under it says in words which part is which).
  - **Chains of steps** (`ol.sp-flow`, three of them here and one on Instructions): a list, so a screen reader hears numbered steps; each step is a box with who acts (the owner, Claude, a script, a reader), a numbered title and a sentence. Six boxes in a row with an arrow between each in a pane of 64rem or more, and one column with a down arrow in a narrower one. The arrows are CSS content with empty alternative text.
  - **Note samples** (`pre.sp-code`): front matter in the host's monospace font, wrapping instead of scrolling.
- **Keyboard and screen readers**: the tabs follow the WAI-ARIA tabs pattern. Only the open tab is in the Tab order; Left and Right move along the tabs, Home and End to the first and last, and Enter or Space opens one (focus moving doesn't open a tab, since a panel draws its tables as it opens and each opening changes the copied link). In each table with Claimed dropdowns or other row controls (Domains, the pathway table, Rate personal competencies, Rating gaps, the job spec scorecard and picker) only one row is in the Tab order: its name, its dropdown and any button in it, so Tab passes the 210-row Rate table in a few presses (about 13 stops on the tab, from about 270). On a row's name, Up and Down move between rows, Page Up and Page Down by ten, Home and End to the first and last, and Left and Right along the row; a dropdown keeps its own arrow keys. Each row's name is its row heading, and in a table with groups every cell names its column, its group and its row (`headers`), so a screen reader says where it is. Tables are named by their card's heading. The timeline and the fit chart are one Tab stop each: the arrow keys move between units (or segments), the one reached is outlined, its tooltip shows and a screen reader hears it; under each chart a closed "as a table" section lists the same rows. The heatmap is a table in both its wide and narrow forms. A hidden live region says what a change did ("Leasing/letting: L3 Advanced, unsaved. 1 unsaved change.", saved, withdrawn, discarded, selection saved); the count line on Rate speaks once typing in Search pauses. Every control has a ring in the text colour when reached from the keyboard (and, with a mouse, a darker edge or text on hover), and the page scrolls so that a control reached with Tab never sits under the sticky bar or a table's sticky heading row. After Save, Discard or Withdraw, focus moves to the save status line or the next Withdraw, or to the open tab once the save bar has closed, rather than dropping to the page.

Every Claimed cell is a dropdown (Not rated, L1 Aware … L4 Expert), so the owner can change a claim wherever they see it.

**An assessor's rating** has an **Assessed** column beside Claimed on Rate personal competencies, the pathway table and the scorecard, and a third scoring basis (**Assessed levels**; "As assessed" in the verdict, the diagnosis and the `job_spec_scores` calc). All of it is out of view (`.sp-assess` off the page's root) until a competency carries a rating, one is saved and waiting, or an assessor is picked: an owner who rates only themself never sees an empty column. Above each of the three tables is **Rate as assessor**, a dropdown of the assessors ("No one" first; a name with its role in brackets), all three showing the same choice: picking someone turns the Assessed cells into dropdowns, and No one closes them. While an assessor is picked, a cell's dropdown is that assessor's own rating and nothing of the others' shows, so each rates without seeing the rest. Otherwise the cell is the **assessed level** as a pill, the lowest of the assessors' ratings (`spAgreed` over `spRatings`: the notes' `assessments`, then each saved change, then each unsaved one, by assessor's name), with who gave what on hover ("Assessed by … on …" for one assessor, a line each for several), and a dash when there is none. Where the assessors differ the pill is followed by a mark, an up-down arrow and the number of levels apart (`differMark`, in the text colour since red and green mean fit; its accessible name gives each rating). The arrow is a small inline SVG, not the character ↕, which comes out a different size in every font; the same markup stands wherever the mark is shown in prose (General definitions, Instructions, How this works). **Rating gaps** also has *Claims above a prerequisite* (`#prereq-gaps`, in view only under `.sp-prereq`, which `spAssessSync` sets when some competency row has `requires`): each claim that stands above the claim for a competency it requires, with both Claimed levels as dropdowns since either may be the one to change, and how many levels below the prerequisite is; it is judged on the levels the dropdowns show, so a row leaves as a level is fixed. Its paragraph on General definitions is under the same class. **Rating gaps** has a further card, *Personal competencies the assessors rate differently* (`#assessor-diff`, in view only under `.sp-assess`): competency, domain, claimed, assessed, levels apart and each assessor's rating, widest difference first, with a line under it when the assessors agree or when no competency has two ratings yet. With no assessors the dropdown is hidden and **Add an assessor** stands in its place, a `data-jump` button that opens Configuration at the Assessors card (a topic button now opens its card's tab when that is not the open one). `spAssessSync` shows the one or the other, and neither while the list loads. A rating is staged, saved, listed and withdrawn by the same code as a claimed level, under the key `assessed--<assessor id>--<key>` with `field: assessedLevel` and `ckey` (the competency's key), and carries the assessor picked when it was made (`by`, the name; `byId`), so each assessor's rating of a competency is its own saved change and two assessors' can be saved together. Heading rows span one more column while the column is in view (`spCols`).

**Assessors** are kept on Configuration (`#assessor-config`, one drawing, `assessorcfg`): a row each with the name, the role and **Edit** and **Delete**; **Add an assessor**, which opens a form (Name, Role (optional), **Save assessor**, **Cancel**; Enter saves) in the button's place; and a status line with **Use the list in your settings file**. There is no draft: Save assessor and Delete it each write the whole list to the store at once (`settings/assessors`, `{list: [{id, name, role}], savedAt}`), since the button pressed says so, and a list put back to the settings file's own is withdrawn (the document is deleted) instead of saved. The page shows the saved list in place of the `assessors` data file until Claude applies it. An id is made from the name when an assessor is added (`spAsrId`: lowercase letters and digits joined by hyphens, accents dropped, `-2` when taken) and never changes, which is how `assessors.py apply` tells a rename from a new person. Delete asks first, in place, and says that the ratings already given stay under the name. A name is required and no two may match, whatever their case; the error sits in the form. What is typed is held in `spAsrEdit`, so a redraw (the save's echo, a change of width) keeps it, and each press says where focus goes next (`spAsrFocus`: the Name field, the row's Edit, Add an assessor).

While a dataset loads, each table, chart and headline number shows a placeholder; if it fails, a quiet "Failed to load" takes its place. The dashboard does not ask again by itself for a file that failed, so while any of the build's data files (`window.spFiles`, which the test holds to the manifest) has failed, a bar shows in the sticky strip, above the save toolbar (`#loadbar`, the red dot of "Failed to load" before its sentence): "Some of this page's data failed to load, so parts of it are empty." and **Reload data**. The button asks for the failed files again, and only those (`dash.refresh`), with no page reload, so unsaved changes stay; it reloads the page only on a dashboard with no such call. While it waits the bar says "Reloading the data…" and the button is off; if a file fails again it says so and that reloading the whole page drops unsaved changes; once every file is back the bar closes, "Data reloaded." is said in the live region and focus goes to the open tab. All three sentences are in the HTML, and `spLoadSync` (run from `dash.onData`) sets only `hidden`, `disabled` and `aria-busy`. A wait counts as over when a file seen loading has stopped, when every file asked for is back, or when a failure is still there 1.5 s after the press; after 20 s the button comes back whatever the dashboard has reported. Instructions lists the mark under *Read the marks*. A table with nothing to list says so in a line under its heading row: "Every rated competency matches the evidence." on Rating gaps, "No competencies match these filters." on Rate personal competencies, a pointer to **Show unrated domains** on Domains (or "No domains in the graph yet." when there are none), and "This pathway lists no requirements." on the pathway table (or, when every requirement is unrated and hidden, a pointer to **Show unrated competencies**); a chart with nothing to draw closes up and says so under it ("No dated units of evidence to draw.", "No units to place by sector.", "No competencies to compare."). Save problems say what happened and what to do ("Saving isn't available right now. Reload the page to try again."; unsaved changes stay on the page after a failed save). A missing value shows as a dash, and a domain name too long for a chart's label column is shortened there, the full name on hover.

The page works from full width down to a phone or a narrow pane beside a chat (about 360px) without the page sliding sideways. There the tabs scroll sideways inside their strip, the open tab brought into view. Only the page scrolls up and down; there are no scroll boxes inside it. Every table's heading row stays just below the sticky bar while the table passes under it (`position: sticky` when the table fits its card; a table wider than its card scrolls sideways in its wrapper, where sticky can't reach the page, so the script moves the heading row down by `--sp-th-y`). In a sideways-scrolling table cells keep to one line, the first column stays put, group labels and rule text stay in view, and the right edge fades while there is more. In a pane under 48rem a level pill shows only its code (L2; the name stays for screen readers, and the Claimed dropdown beside it shows it in full), so Domains fits Domain, Claimed and Supported with its marker at 400px. Rate personal competencies, Rating gaps and the assessors' differences fit the same three there: under 40rem their Domain column is left out (`.sp-cdom` on its heading and cells), each row's domain sits under its name (`span.sp-dom`, which `domLine` writes into the row heading and a wider pane hides), and a "Use LX" button goes under its dropdown instead of beside it. From 40rem the table has room for the Domain column, and a name with its domain under it would only make every row taller. A table's first columns are the ones in view in a narrow pane, so the answer goes there: Band and Promotion in the verdict, Result in the scorecard, Evidence in the pathway table. Prose (card notes, footnotes, rule text, definitions) keeps to about 64ch. On a touch screen every control is at least 44px tall; with a mouse at least 24px, and a whole Configuration row ticks its box.

## Page versions

The page and the plugin share one version number, apart from the specification's and from anything claude.ai counts. On the page it is written once, in the template's header (`<p class="sp-version" id="page-version">Version X.Y.Z</p>`), so every owner's dashboard shows which release of the plugin built it; `dashboard_build.py` reads it into the manifest (`pageVersion`), prints it, and stops if the template shows none. It is not one of the owner's settings and has no `kg:` marker.

The same number is in the plugin's manifests (`.claude-plugin/plugin.json`, `marketplace.json`), at the head of the plugin's `CHANGELOG.md`, in the README's badge and table, and on the release's git tag (`vX.Y.Z`). `tools/bump_version.py X.Y.Z "What changed."` writes it in all of them, with `--page "…"` for what changed on the page; `test_versions.py` fails if any two disagree. Until 2026-11-15 the page was numbered alone and the plugin separately (0.1.0, 0.1.1); the plugin took the page's number at 1.7.2.

So the number moves with every release, whether or not the page changed. Add a line here for each, newest first (`test_dashboard.py` checks that the newest line is the template's number); a release that leaves the page as it was says so in its line. What changed outside the page is in `CHANGELOG.md`.

- **Patch** (1.0.x): a fix or a rewording that changes nothing a reader or an owner does, on the page or in the skill, its scripts or its library.
- **Minor** (1.x.0): something new to see or use: a tab, a card, a column or a control on the page; a script, a command, a framework or a field in the skill.
- **Major** (x.0.0): data files, store documents, settings or notes in a new shape, so a dashboard must be rebuilt and its saved changes applied first, or an owner's files migrated.

## Build markers

`scripts/dashboard_build.py` turns the template into the owner's page; nothing in the page is edited by hand. It finds its places by comment markers, which stay in the built page:

- `<!-- kg:title -->`, `<!-- kg:sectors -->`, `<!-- kg:practitionerMonths -->`, `<!-- kg:advancedYears -->`, `<!-- kg:expertYears -->`, `<!-- kg:expertRecognition -->` and, in the timeline script, `/* kg:staleYears */`: a value from the config's `dashboard:` block or the profile, written between the opening and closing marker (`<!-- /kg:title -->`).
- `<!-- kg:fw -->` … `<!-- /kg:fw -->` (in a script, `/* kg:fw */` … `/* /kg:fw */`): cut for an owner with no frameworks. A marker on its own line cuts whole lines; one inside a sentence cuts the words between, so the sentence must read right both ways ("…against the professional frameworks chosen on Configuration and the roles defined on Job specs" without the framework words). The two framework tabs and their panels, Configuration's frameworks card (the tab itself stays, for the assessors), the `framework_pathway` and `competency_definitions` calcs, the two General definitions items on framework pathways, the Instructions lines and card on frameworks, the framework words of the How this works `settings` row and drawing, and the header's framework words are marked; the framework drawings stay, and never run.
- The template is one file; the build writes it in parts. `dashboard_build.py` moves the `<style>` to `dashboard.css` and each `<script>` to `dashboard-N.js`, which `index.html` loads in the same order, because the dashboard's store holds at most 256 KB a document and the template in one piece is over that (so `--one-file` now stops with an error for the shipped template). So a `<script>` here is a file there: keep each one a scope of its own, sharing through `window`, and split one that grows past about 150 KB. `index.html` cannot be split, since the Dashboard type takes one HTML file and no script may write a tab's words: it holds every tab, and the two explaining tabs (Instructions, How this works) are about half of it. It was 62% of the limit at page 1.4.0; the build says so at 80% and the test fails there, and the place to cut then is those two tabs' prose and drawings.
- `/* kg:jobscore */` … `/* /kg:jobscore */`: the scoring block (`window.spJob`), which the tests run in Node against `job_specs.py`. Keep the two the same.

`scripts/tests/test_page_browser.py` runs the built page in Chromium (Playwright; d3 from `tests/vendor`; the page run by `tests/page_shim.py`): every tab at 1280px and 400px with no script error and no sideways slide, the three charts drawn, the timeline's two ranges, and the controls jsdom can't lay out. It stands in for the Dashboard type's tokens with plain values, so it checks that the page works and fits, not its look on claude.ai. The type's real stylesheet also resets every element (a `ul` or `ol` loses its markers, a `figure` its margins), which the stand-in does not: a list of prose sets `list-style` itself (`.sp-ref`, `.sp-howto`, `.sp-dtext`), and anything new that leans on a browser default needs a look under the real stylesheet.

**Look at the page before publishing a change to it.** `scripts/tests/render_page.py --css app.css` runs the built page with the type's real stylesheet and writes a picture of every tab at 1280px and 400px, light and dark (`--tab`, `--width`, `--scheme` narrow it; `--cards` adds a picture a card; without `--bundle` it builds the dashboard from the config). It reports a script error, a page that slides sideways, and each list that has markers under the stand-in tokens and none under the real stylesheet, and exits 1 on any of them. `app.css` is the host's file and changes, so it is not kept in the skill: save it from a published dashboard with the Artifact tool (`action: read`, the dashboard's url, `path: artifact-type/app.css`). The pictures are the point, since a report can only name what it was written to look for: read them.

A new owner-specific value gets a marker, a line in `VALUES` in `dashboard_build.py` and a test. Text that should vanish without frameworks gets `kg:fw` markers, and `test_dashboard.py` checks the page without them.
